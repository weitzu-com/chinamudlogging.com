## 转化结论的边界

正式漏斗在 2026-11-04 才启用。本次基线仅 1 次正式访问（direct）、0 意向、0 收件、0 有效询盘；测试收件排除。历史 GSC 点击与新漏斗观测没有重叠窗口，不能计算历史 Google→收件/有效询盘率，更不能把 0/12 宣称为真实转化率。没有意向/收件分母时，转化率为 null，不写 0%。

第一瓶颈是可观察到的搜索获客规模不足：28 天仅 12 点击，平均排名 15.8。第二瓶颈是来源/落地页到商业结果的分析能力缺口。准备邮件依赖邮件客户端是可改进的交互摩擦，但尚无流失数据证明它是最大业务瓶颈。有效率目前不可判断；自动收件不代表人工有效审核已发生。

## 本轮实现

1. 首页 title/H1 明确 mud logging equipment、units、sensors；目录 title 明确设备和传感器，去掉面对客户的代码恢复文案。
2. 流量最高的 mud-logging-units 分类增加配置要点、预填产品 RFQ 入口和传感器比较入口，不新增未经验证的性能/交期承诺。
3. 联系页新增 Copy inquiry text 和始终可见的准备后文本，方便使用网页邮箱。明确仍需自行发送。复制和准备邮件使用同一 requestId，避免重复意向；均不创建 receipt。
4. 浏览器仅将 Google 引荐域名归为 google；其他搜索仍为 search，历史 search 不重分类。缺失引荐信息仍可能归 direct，不伪造 Google 来源。
5. 报表增加 source × landing_path，访问/意向会话/意向/实际收件/有效/待审分组；关联原访问 cohort、排除测试，审核只取最新决定。每组 first_visit 明确真实观测起点。HTML 报表同步显示分组。

## 验证与后续对照

`npm run verify`：5 个链路测试、Astro 检查和构建、84 个 HTML 检查及依赖审计通过。分组测试覆盖重复事件不放大、收件后待审、人工审核后变更。浏览器本地验证了产品预填、复制文本及“未发送”提示；本地测量关闭，未增加正式流量。生产发布结果见同目录后续记录。

未来对照使用完整重叠窗口，建议首个完整 28 天为 2026-11-05 至 2026-12-02，等待 Google 数据延迟后再比较。GSC 按美国太平洋日，漏斗按 UTC，周/月汇总需保留时区差异；GSC 点击不是 JS 匿名会话，不直接当漏斗分母。每周按 google × landing_path 查看意向率、收件率和人工有效率，销售先处理 pending_review；样本不足时继续显示样本数，不宣称统计提升。

官方口径：[Search Console 数据及延迟/时区](https://support.google.com/webmasters/answer/96568)、[查询数据差异](https://support.google.com/webmasters/answer/17010575)。普通产品页不适用 Google Indexing API，仅使用 sitemap 和 Search Console URL 检查，不使用 JobPosting/BroadcastEvent 专用 API。
