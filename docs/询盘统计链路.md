# 询盘统计链路：规格、操作与验收

## 需求规格

- 目标：能核实每个阶段，不将准备邮件或点击按钮当作已送达询盘。
- 受众：经营者和销售审核人员；访客继续使用原有邮箱询价流程。
- 技术栈：Astro 静态页面 / Vercel 同源转发 / Cloudflare Worker / D1 / Node 24 操作工具。无需 GA4、GTM、收费分析订阅或新表单供应商。
- 交付：页面及产品浏览、联系页浏览、邮件准备和联系方式点击事件；受保护的收件及审核接口；JSON/HTML 经营报表；自动测试；生产验收记录。
- 约束：不采集表单内容、联系人、完整 URL/查询串/来源网址；数据库不保存 IP/UA；90 天保留期；测试隔离；收件和有效性判断不得由公开客户端写入。
- 复用：既有 Astro 页面与 verify CI；Zoho 投递日志；现有 Node 24 发布门禁；《网站GA4-GTM跟踪诊断》中的一手验真方法。独立单元按“采集→证据→审核→报表”流水实施。

## 口径与状态

| 阶段 | 触发与证据 | 权限 | 去重 |
|---|---|---|---|
| 访问 | 已落库 page_view；30 分钟、浏览器 tab 内匿名会话 | 公开窄字段接口 | session UUID + event UUID |
| 询盘意向 | email_prepare / email_click / phone_click | 公开窄字段接口 | session + request UUID |
| 实际收件 | Zoho 状态 Delivered；Message-ID 匹配实际邮件；邮件内 CML 编号匹配意向 | 管理员核验后导入 | 一个意向一条收件；Message-ID 哈希全局唯一 |
| 有效询盘 | 收件后，销售人工判断有相关用途/采购需求 | 管理员记录审核分类 | 追加审核历史，最新决定生效 |

只打开草稿的意向一直停在第二阶段，不自动晋级。电话点击也不能导入邮件收件。收件后默认“待审核”，不自动成为有效询盘。测试原因 `test_fixture` 只允许测试会话。

“有效”标准：需求与录井设备/传感器业务相关，存在可跟进的具体用途或商业需求；垃圾邮件和无关内容排除。销售在邮箱查看内容后选择 `application_fit` 或 `commercial_requirement`；不把邮件正文交给统计服务。

报表以访问日期的 UTC cohort 归属，后续收件及审核会回填原日期。访问→意向与意向→收件按会话计算；收件→有效按询盘计算，分母不混用。分母为零时为 null/—。默认排除测试。

匿名会话不是人数；拒绝测量、DNT/GPC、拦截器、未带编号的直接邮件都可能造成缺口。不倒填历史转化率，不把未归因邮件假装归入网站漏斗。

## 运营操作

操作密钥只在本机 `~/.config/chinamudlogging-funnel/admin.json`（0600）和 Worker secret 中，不进入 Git、网页、命令参数或报表。以下命令在本项目目录执行。

### 1. 查看正式报表

```sh
node scripts/funnel-admin.mjs report --from 2026-11-04 --to 2026-11-30 --out .source-private/reports/funnel.json
```

生成 JSON 和同名 HTML，均含时间范围及统计限制。`--test` 才显示测试。查询最长 90 天。

### 2. 登记实际收件（每日销售查看邮箱时执行）

在 Zoho `sales@cnps.com` 邮箱（别名 `sales@chinamudlogging.com`）打开新询盘，核对主题/正文中的 `CML-<UUID>`。在管理员投递日志中找到同一 Message-ID，确认收件地址、Delivered、时间和垃圾邮件状态。保留证据在 `.source-private/receipts/`，不要提交公开仓库。

保存如下 JSON，字段必须来自实际邮件与日志；`operatorVerified` 表示操作人已完成上述核对，不是程序自动证明：

```json
{
  "inquiryId": "邮件中 CML- 后面的 UUID",
  "referenceInMessage": "CML-完整UUID",
  "messageId": "<实际邮件的Message-ID>",
  "deliveredAt": "2026-11-04T05:20:00.000Z",
  "source": "zoho_delivery_log",
  "recipient": "sales@chinamudlogging.com",
  "status": "Delivered",
  "operatorVerified": true
}
```

```sh
node scripts/funnel-admin.mjs receipt --file .source-private/receipts/实际证据.json
```

CLI 在本地对证据做 SHA-256；服务仅保存指纹和 Message-ID 哈希。重复登记不会增加数量。无对应网站编号的邮件留在销售业务记录中，不通过伪造意向补进网站漏斗。

已部署组织 SMTP 日志只读轮询，配置、权限和真实验收状态以 [Zoho自动收件同步](./Zoho自动收件同步.md) 为准。人工证据登记保留作补录；只有关联编号和真实投递证据同时成立才计入收件。

### 3. 审核有效性

```sh
node scripts/funnel-admin.mjs qualify --inquiry UUID --decision qualified --reason commercial_requirement
node scripts/funnel-admin.mjs qualify --inquiry UUID --decision rejected --reason spam
```

可用原因：有效 `application_fit` / `commercial_requirement`；排除 `not_relevant` / `spam`。纠正决定时追加一次新审核，保留旧历史；重复请求可传同一 `--review-id UUID`。

### 4. 定期对账

每天检查 `zoho-status` 及带编号的新邮件，自动关联未完成时与投递日志核验补录；检查报表 `pending_review`；每周抽查已登记 Message-ID 与邮箱，核实无重复。无法关联或同步遗漏的已收邮件须核验补录。浏览器未记录或旧编号已超过 90 天时，保留业务收件记录，不伪造漏斗访问。

## 验证与部署

`npm run verify` 先测试：意向不晋级、无收件不审核、鉴权、跨来源拒绝、隐私字段拒绝、重复收件、重复审核、审核纠正、会话过期和测试隔离；再运行 Astro 构建、元数据/内链检查及依赖审计。

Worker 配置在 `workers/funnel/wrangler.jsonc`；数据库迁移在 `schema.sql`，部署前先应用。管理密钥通过 `wrangler secret put` 安全输入。Worker API 先部署，之后经 PR 发布 Vercel 转发与前端。Worker 代码变更需要独立部署，Vercel 不会替它部署。

```sh
wrangler deploy --config workers/funnel/wrangler.jsonc
```

匿名采集遵守 DNT/GPC，提供 `/privacy/` 中的关闭入口。关闭采集不影响原有邮件流程。管理接口只接受密钥，不启用跨域读取。公开字段白名单、正文 4 KB 上限、短期签名会话、请求限流和每会话上限抑制误用；不能宣称彻底识别所有机器人。

测试会话由管理接口创建：

```sh
node scripts/funnel-admin.mjs test-session --out .source-private/test-ticket.json
```

打开返回测试链接，依次浏览产品与联系页、准备测试邮件。确认测试报表中意向增加而收件/有效仍为零。实际发送带该编号的测试邮件，待 Zoho Delivered 后登记，再以 `test_fixture` 审核测试记录。重复登记确认不增量。最终核对正式报表没有混入测试数据。

## 回滚与维护

前端统计故障会退回原有 mailto，不向客户谎报已发送。关闭采集可移除 BaseLayout 的脚本入口；数据库与证据保留供对账。修改 Worker 要先运行测试、部署，再验收健康接口、无鉴权 401、意向/收件分离和报表。

Cron 每天清理超过 90 天会话及其关联记录。网络供应商有平台自身日志及请求元数据处理，不将“应用库不存 IP”宣称为整个网络链路从不处理 IP。
